# Негативные тесты регистрации и требования безопасности

Набор проверяет поведение HTTP-обработчиков и изменения данных в PostgreSQL.
Выполняются 15 тестовых случаев, включая варианты параметризованных тестов.
Отправка писем заменена тестовой функцией: она сохраняет текст письма в памяти
либо воспроизводит заданный сбой. Реальные письма не отправляются.

## Проверяемые требования

| Код | Требование безопасности |
|---|---|
| SEC-01 | Повторная регистрация не создаёт второй аккаунт и не изменяет пароль или статус существующего пользователя. |
| SEC-02 | Пользователь с неподтверждённой почтой не получает сессию входа и доступ к кабинету. |
| SEC-03 | Просроченная, заменённая или уже использованная ссылка не подтверждает почту. Подтверждение одноразовое. |
| SEC-04 | Одновременные запросы сохраняют уникальность аккаунта, одноразовость подтверждения и единственный действующий токен после повторной отправки. Подтверждение и повторная отправка не блокируют друг друга навсегда. |
| SEC-05 | Сбой отправки письма не подтверждает аккаунт и не даёт доступ. Созданную регистрацию можно продолжить после восстановления почтового сервиса. |
| SEC-06 | Ответы и журналы приложения не раскрывают текст SMTP-ошибки с потенциально чувствительными данными. Повторная отправка возвращает одинаковое сообщение для неизвестного, подтверждённого и неподтверждённого адреса, в том числе при сбое почты. |

SEC-06 относится к форме повторной отправки. Регистрация существующего адреса
по текущим требованиям возвращает отдельное сообщение о занятой почте.

## Связь тестов с требованиями

Все тесты находятся в `tests/test_security.py`. Имена ниже можно использовать
для запуска отдельного сценария через `pytest -k`.

| Тест | Подготовка и действие | Ожидаемый результат | Требование |
|---|---|---|---|
| `test_existing_email_does_not_overwrite_account` — два варианта | Создан подтверждённый или неподтверждённый аккаунт. Повторная регистрация той же почты с другим паролем. | HTTP 400; остаётся одна запись; прежние хеш пароля и статус сохранены; письмо не отправляется. | SEC-01 |
| `test_unverified_account_cannot_login_or_open_account` | Вход с правильным паролем аккаунта, у которого `email_verified=false`, затем запрос кабинета. | Вход возвращает 403; кабинет перенаправляет на `/login`; статус аккаунта не меняется. | SEC-02 |
| `test_expired_link_does_not_activate_account` | В базе задан `expires_at` в прошлом. Открытие ссылки, попытка входа и повторное открытие ссылки. | Ссылка возвращает 400; токен удалён; почта не подтверждена; вход запрещён. | SEC-02, SEC-03 |

| `test_used_link_cannot_be_replayed` | Одна действительная ссылка открывается дважды. | Первый запрос успешен, второй возвращает 400; токен отсутствует. | SEC-03 |
| `test_concurrent_registration_creates_one_account` | Два запроса регистрации одной почты одновременно ожидают блокировку таблицы, затем продолжаются. | Один ответ 303, другой 400; одна учётная запись, один токен и одно письмо. | SEC-01, SEC-04 |

| `test_concurrent_resend_leaves_one_active_token` | Два запроса повторного письма одновременно ожидают блокировку пользователя. | Оба ответа нейтральные; в базе один токен; из двух новых ссылок только одна соответствует сохранённому хешу; исходная ссылка отклоняется. | SEC-03, SEC-04 |
| `test_confirmation_and_resend_have_consistent_result` — два порядка запуска | Одновременно выполняются подтверждение старой ссылки и повторная отправка. | Нет исключения или зависания. Если подтверждение победило — токенов нет; если первой была замена — старая ссылка отклоняется, новая работает. | SEC-02, SEC-03, SEC-04 |
| `test_mail_failure_keeps_account_unverified_and_allows_retry` — три ошибки | При регистрации воспроизводятся таймаут, обрыв SMTP и отказ аутентификации отправителя. Затем почтовый сервис восстанавливается. | Ответ 503 со ссылкой повторной отправки; аккаунт сохранён неподтверждённым; вход закрыт. После нового письма подтверждение и вход проходят. Детали SMTP скрыты. | SEC-02, SEC-05, SEC-06 |
| `test_resend_failure_is_neutral_and_can_be_retried` | Ошибка отправки для неподтверждённой записи; сравнение с неизвестным и подтверждённым адресами; повтор после восстановления. | Одинаковые ответы 200; детали ошибки скрыты; статус остаётся false; новое письмо позволяет завершить подтверждение. | SEC-02, SEC-05, SEC-06 |

У каждого теста есть отметка `@pytest.mark.security(...)`. Pytest переносит её
в свойство `security_requirement` отчёта JUnit XML. При добавлении теста без
такой связи сборка останавливается с ошибкой.

## Как проверяются гонки

Тест удерживает блокировку в отдельной транзакции, запускает HTTP-запросы
и через `pg_stat_activity` проверяет, что оба запроса действительно ждут
блокировку PostgreSQL. После её освобождения проверяются ответы и данные.
Один лишь одновременный запуск Python-задач не считается доказательством гонки.
Ожидания ограничены по времени, чтобы зависание завершало тест ошибкой.

Подтверждение и повторная отправка блокируют строки в одном порядке: сначала
пользователя, затем токены. После ожидания подтверждение заново ищет токен,
так как за это время другая транзакция могла заменить или удалить ссылку.

## Запуск

В активированном окружении проекта установите зависимости тестов

```bash
python -m pip install -r requirements-test.txt
```

Подготовьте отдельную базу `visitor_registration_test` в PostgreSQL с владельцем,
который может создавать в ней схемы. Создайте локальный `.env.test` по образцу
`.env.test.example` и заполните `TEST_DATABASE_URL` строкой подключения к этой базе.
Пароль и остальные значения берутся из вашего тестового подключения.

```bash
python -m pytest -v --junitxml=security-test-results.xml
```

Рабочая база не очищается: имя тестовой базы должно заканчиваться на `_test`.
Каждый тест создаёт собственную схему со случайным именем и удаляет только её.
Файл приложения `.env` не читается при импорте тестируемого модуля и не изменяется.
`.env.test` исключён из Git, в репозитории хранится пустой образец.

В GitHub Actions PostgreSQL запускается отдельным сервисом. Результаты
публикуются как артефакт `security-test-results`. Сетевые ограничения Gmail
и фактическая доставка писем этим набором не проверяются: их проверяют отдельно
на рабочем компьютере.

## Что изменено в обработчиках

При сбое первичной отправки вместо необработанного исключения возвращается
страница с HTTP 503 и переходом к повторному письму. Пользователь и токен
сохраняются, признак подтверждения остаётся false. В журнал попадает класс
ошибки без её текста. При повторной отправке публичный ответ остаётся нейтральным.

Повторная отправка и подтверждение выполняются с блокировкой строки пользователя
в транзакции. Это не позволяет двум повторным отправкам оставить две действующие
ссылки и согласует замену ссылки с её одновременным подтверждением.
